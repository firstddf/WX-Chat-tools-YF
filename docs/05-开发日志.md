## 2026-11-07 二轮 · P0 图片懒解码收口 + 状态行 Tk 口径（M-A3 #9 收口）

### 1. 根因与方案（三选一取「懒解码」）

上轮遗留：`resolve_media=true` 大账号首解 4700+ 图 ≈**6.9 分钟** > `LOAD_TIMEOUT` 300s
（壳判超时 `迟到或未知的应答`，前端拿不到数据 → 图片永远看不到）。三个候选里取**懒解码**：

- ❌ 超时提到 ~900s + 解码进度：只是把 7 分钟等待延后，冷缓存重跑仍要等（解码不落盘判断不存在——`decode_dat` 每次都跑）；
- ❌ 后台解码 + ready 事件：可见缩略图仍可能排在解码队尾，首屏体验不保证；
- ✅ **懒解码**：加载期图片**只定位不解码**，缩略图滚进视口再按需解码（Tk 没这个问题纯粹因为它阻塞式无超时，不代表体验好）。

契约（**docs/02 v1 兼容增补**，字段形状不变）：

- `load_source options.resolve_media=true`：文件/视频/语音照常解析；图片只定位
  （`media[].decoded=false`、`path=""`，name 为 `.dat`/`md5.dat`），**解码缓存已有的直接回填
  `decoded=true`**（热路径零成本）；`ensure_image_key` 仍在加载期；
- 新方法/命令 **`resolve_media` `{indexes}` → `{items:[{index, media}]}`**：按需解码，
  与 load/export 同一把互斥锁（`EXPORTING_BUSY`），未挂 resolver 时原样返回（前端停止重试）；
- `export` 写出前为导出子集补齐未解码图片（对齐 Tk 导出 path 齐全），每 ~50 条发 progress
  → `EXPORT_TIMEOUT` 300s→**900s**；壳新增 `RESOLVE_TIMEOUT`=60s（前端每批 ≤32 条）。

### 4. 期间修掉的四个真 bug（都是真机/大数据下才暴露）

1. **加载超时 60s 太短**：大账号 400+ 会话（3 万+ 条）在「读取会话全部」之后仍被壳判超时
   （前端 `detail=load_source 超时（60s）`，用户感受就是"卡了"）。`LOAD_TIMEOUT` 60s→**300s**
   （docs/03 §3 同步；进度事件已能看，超时只做兜底）。实测同样本加载 23.8s，但冷缓存 + IPC 大 payload 会顶到 60s 以上。
2. **错误行渲染成 `[object Object]`**：`FilterPanel.statusLine` 里把 `ComputedRef` 直接塞进模板字符串
   （模板插值才会自动解包 ref）。改取 `.value`。
3. **sidecar 被外部终止后壳永久卡死**：`SidecarManager::log` 用 `println!` 写 stdout；dev 启动时
   stdout 是管道、读端已关闭 → Rust `println!` 写失败会 **panic**，打死 stdout/stderr 读线程与
   `handle_exit`，锁被毒化后日志全静默 → 壳一直以为 sidecar `ready`，之后每次调用都
   `等待 sidecar 进程就绪超时（5s）`。修法：① 改非 panic 写（`writeln!` + 忽略错误）+ 锁毒化也继续写；
   ② 新增**进程看门狗**（每秒 `try_wait`，兜住漏掉的 stdout EOF）→ 统一走 `handle_exit` 自动重启一次/置 failed。
   实测：kill 掉 sidecar 后日志出现 `sidecar 进程退出（gen=0）` → 自动 `gen=1` 重启 → `握手成功: state=restarted`。
4. **壳 `[dbg]` 诊断行残留 + 握手 2s 踩线**：`[dbg]` 全剥离（cargo check 0 warning）；握手 2s→5s
   （docs/03 定稿，依据 Python 冷启 2.0–2.3s）。docs/02 §2 `status→state` 核对后确认文档早已对齐，无需改。
